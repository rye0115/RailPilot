## 3. 许可证审计：能不能复制

**这是“参考/复制”的第一道门槛。** 没有 LICENSE 的仓库，默认适用著作权法“保留所有权利”，不能复制、修改、再发布；README 写“开源”不等于授权。**本项目的选择是：即使许可证允许，也只参考算法/流程，不复制代码。**

| 类型 | 项目 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **MIT** | c66-m、RailWatch、12306-helper、ticket_helper | fork、修改、再发布、商用（保留版权声明） | 去掉版权声明；作者不承担担保 |
| **Apache-2.0** | py12306、nageoffer/12306 | fork、修改、再发布、商用（保留 NOTICE/专利条款） | 用作者商标；去掉许可文本 |
| **未声明** | 12306FairTicket、easy12306、12306ForMac、Joooook/12306-mcp、gzldc、V-I-C-T-O-R、Why8n、e1roy、yinaoxiong、versionzhang | 读代码、提 PR、按功能自行实现 | 复制代码、fork、打包再发布 |
| **闭源** | Bypass | 用官方发布版、读帮助文档 | 反编译、复制、二次分发 |
| **官方** | 12306 | 按用户协议个人使用 | 批量抓取、自动化高频访问、商用 |

### 3.1 重点项目的许可证细节

- **c66-m/12306-ticket-monitor**：顶层 `LICENSE` 为 MIT（Copyright 2026 c66-m）。许可证允许 fork，但本项目**只参考**，不复制代码。
- **RailWatch-12306**：顶层 `LICENSE` 为 MIT（Copyright 2026 RailWatch 12306 contributors）。许可证允许 fork，但本项目**只参考**隐私文档/架构。
- **12306-helper**：顶层 `LICENSE` 为 MIT。许可证允许复用，但本项目**只参考**扫码/锁座/支付页流程，不复制存储层。
- **py12306**：Apache-2.0；只参考通知/配置/Web 的信息架构，不建议作为参考实现。
- **12306FairTicket**：README 写“开源购票助手”，仓库树里只有 `docs/licenses/` 下的第三方许可证（Qt/OpenSSL/Python），**没有顶层 LICENSE**。在法律上默认“保留所有权利”。**不要 fork、不要复制代码**；可以给作者提 Issue/PR 请求加 LICENSE，或只参考产品设计。
- **Bypass**：闭源免费，官网明确“所有功能完全免费，只有 Windows 版”。只能当功能标杆。

### 3.2 Qt/PySide6 的许可证

`12306FairTicket` 的 `docs/licenses/` 同时列了 Qt GPL-2.0/3.0 和 LGPL-3.0。如果你 fork 一个 PySide6/Qt 项目并分发，需要遵守 Qt 的 LGPL/GPL 条款（动态链接、提供替换库的方式、附许可证文本等）。个人自用风险低，公开发布前要做合规审查。

## 4. 重点竞品拆解

### 4.1 testerSunshine/12306（34k，已归档）

**它是什么**：2017 年出现的 Python 抢票脚本，2019 年火到 GitHub 趋势第一。支持自动打码、自动登录、准点预售、捡漏、智能候补、邮件/Server酱通知。

**为什么不能用**：
- 已归档（archived），最后 push 2023-04-02；README 写明只支持 Python 2.7.10–2.7.15 / 3.6–3.7.4。
- 依赖 `tensorflow==1.14.0`、`keras==2.2.4`，现代 Python 装不上；本地打码模型是 2018 年的。
- 登录依赖 `RAIL_DEVICEID` / `RAIL_EXPIRATION` 手工抓 Cookie，12306 的设备指纹和风控早已换代。
- 代码里还有 CDN 探测、代理等 2019 年的“加速”思路，今天更容易触发风控。

**能不能参考**：不能作为实现基础；只能读主流程拆分（查询 → 下单 → 通知）和“预售/捡漏双模式”的产品思路。**不要参考**打码、Cookie 手工注入、CDN IP 轮询。

### 4.2 pjialin/py12306（15k，维护弱）

**它是什么**：2019 年的分布式购票助手，支持多账号、多任务、多线程、多日期、单任务多站点、Redis 主从、Docker、Web 管理页、邮件/语音/钉钉/Telegram/ServerChan 通知。

**现状**：
- 最后 push 2026-10-01，但核心代码仍是 2019 年的；196 个开放 issue，23 位贡献者，GStars 健康度 19/100。
- 自动打码只剩 `free` 共享平台，平台是否可用不稳定；Docker 镜像最后更新约 6 年前。
- 多账号 + 分布式 + 代理池的设计，正好是 2026 年监管和风控的重点。

**能不能参考**：Apache-2.0，可以**参考**通知适配器、配置热更新、Web 管理页的信息架构；不要参考核心下单、打码、多账号、代理池。

### 4.3 Tuan-Space/12306FairTicket（93★，2026 活跃，许可证未声明）

**它是什么**：2026-04 创建、2026-09-29 更新的 Windows 桌面购票助手，Python + GUI/CLI，提供便携版 EXE。

**核心功能**（来自 README）：
- **服务器时间校准**：多次采样，选网络往返最低的样本，补偿本机时差。
- **开售前准备**：提前复查登录、再次校时、查询热身。
- **发现余票自动提交**：按设定顺序尝试备选，任一订单成功后停止。
- **多站点购物车**：不同车站、车次、席别一起备选，拖动调整顺序。
- 成人/学生票、座位/铺位偏好、配置保存、深浅主题。

**评价**：产品结构最接近本方案，代码可读，适合当“产品参考”和 upstream PR 目标。**但许可证未声明，不能直接 fork/复制**。正确做法：
1. 给作者提 Issue：请求补充 LICENSE（建议 MIT/Apache-2.0）；
2. 在许可证明确前，只读 README/文档，按功能自行实现；
3. 如果作者接受，优先把“候补编排/支付护栏”作为 PR 提上去，而不是另起 fork。

### 4.4 c66-m/12306-ticket-monitor（2★，MIT，2026-11）

**它是什么**：Electron 桌面壳 + Python 后端，免登录轻客户端轮询余票；命中后用 Playwright 驱动真实 Edge 自动提交订单（不支付）；订单结果用官方接口回读 + 时间戳归因，避免重复下单；支持多任务、定时开抢、预热、“车次=席别”规则。

**为什么值得参考**：
- **MIT**：许可证允许 fork；但本项目只参考流程，不复制代码。
- **真实浏览器**：复用用户已登录的 Edge 上下文，减少伪造终端特征。
- **订单回读 + 时间戳归因**：解决“提交超时但实际成功”的幂等难题，这是很多老项目没有的。
- **免登录查询**：查询和下单分离，降低登录态被查询打掉的风险。
- **架构新**：2026-11 还在更新，比 2019 年的 py12306 更贴近当前页面/风控。

**局限**：星极少，代码新，未经过大流量验证；**会话 Cookie 明文**；**`AutomationControlled` 反检测**；第三方 IP/FOFA 查询。详见 `docs/08-security-audit.md` 的 F-01~F-04。

### 4.5 lyt26/12306-helper（0★，MIT，2026-09）

**它是什么**：Python + GUI，扫码登录、查余票、监控锁座、带登录态打开支付页；不收密码、不自动付款；Windows 安装包 + Android 工程。

**为什么值得参考**：
- **MIT**：许可证允许复用；但本项目只参考流程，不复制存储层。
- **最小权限**：不收账号密码，只扫码；Cookie 只存本机。
- **锁座 ≠ 买到**：README 明确“锁座只是官网帮你留座，一般 30 分钟内自己付款”。
- **一账号一单**：明确“同一时间只能有一笔未完成订单”。

**局限**：星 0，代码新；**Cookie 明文**；**支付 profile 持久化**；Android 端用密码登录。详见 `docs/08-security-audit.md` 的 F-05/F-06。

### 4.6 Bypass 分流抢票（闭源，用户最多）

**它是什么**：2013 年诞生的 Windows .NET 抢票软件，免费、无 Mac/手机版；一个机器最多开 3 个实例；支持多任务、多车次/乘客/日期/席别、候补、选座/选铺、学生/儿童票、自动支付、邮件/微信/QQ/webhook 通知、CDN、增开车次。

**2026 现状**：
- 官网更新日志最后一条是 2026-02-27 的 v1.16.68；更新内容只是修 bug。
- 2026-01-21 的 v1.16.67 还加了“自动支付可显示支付窗口”；功能确实全。
- 社区反馈（2026-09，LINUX DO）：Bypass 提交后没抢到，手动在手机 App 却抢到了；热门软卧排队约 50 秒后提示没票，手机端仍可抢。作者认为可能被风控针对。
- 官网帮助自己写：“官方 APP 排队时间更短、优先级高一些，而软件是基于官网的。”这句话很关键。

**能不能参考**：闭源，不能参考代码；只做功能标杆（多任务、候补提示、选座/选铺、通知、维护时间自动暂停、防休眠）。**不要学**：CDN 轮询、自动支付默认开、长时间低间隔刷票、多开。

### 4.7 官方 12306（真正的基线）

不是“竞品”，是唯一官方渠道。它已经提供：
- 购票信息预填（起售当日提前选人/车次/席别，起售一键提交）；
- 起售提醒订阅；
- 候补购票（6 单 × 3 日期 × 60 车次，接受新增列车，24 小时兑现）；
- 京沪高铁/京沪铁路预约购票试点（开车前 30–17 天，精确/模糊预约）；
- 2025 春运试点过“预支付 + 系统自动提交订单”，未宣布全国常态化。

**结论**：任何第三方工具的上限，都是“替你在官方页面上更快地点一次”。官方能力才是主力。

## 6. 他们做对了什么

1. **把“开售时间”当成一等公民**：12306FairTicket、TopF1ag、Bypass 都在校时/倒计时/预热上投入。
2. **多备选优先级**：车次、席别、日期、车站按用户偏好排序，成功后立即停止；这是提高命中率最朴素也最有效的手段。
3. **候补产品化**：Bypass 把候补当独立流程，提示“第一时间候补、第一时间支付”；py12306 把候补与刷票并行。
4. **订单结果回读**：c66-m 用官方接口回读 + 时间戳归因，避免“超时但成功”导致的重复下单；老项目普遍缺这一层。
5. **通知闭环**：邮件、微信、QQ、Telegram、webhook、语音；抢到后 30 分钟内必须让人知道。
6. **隐私最小化**：12306-helper 扫码登录、不收密码、Cookie 本地；RailWatch 明确“登录验证码和支付由用户手动完成”。
7. **解释失败**：Bypass 帮助中心区分“缓存票”“区间限售”“未放票”“排队人数大于余票”，比单纯报“失败”有用。

| 打码军备竞赛 | 验证码模型年年失效，共享打码平台停服 | 不把验证码识别作为核心能力；用扫码登录 + 人工介入 |
| 高频轮询 | IP 被封、账号进慢速队列、提交被拒 | 低频 + 抖动 + 退避；售罄后转候补，不刷 |
| 多账号/代理池 | 被判定异常、批量封号；法律风险 | 单账号、本人乘车；不做账号池/代理池 |
| CDN IP 扫描 | 拿到的 IP 不可信，反而被风控 | 用官方域名，不做 IP 轮询 |
| 重复下单 | 提交超时后重试，生成两笔订单 | 幂等键 + 订单回读 + 未支付订单检查 |
| 自动支付默认开 | 误买、重复买、退款麻烦 | 默认人工支付；自动支付必须显式授权 + 限额 |
| 页面改版 | 选择器失效，整工具报废 | Page Object + 每日冒烟 + 选择器集中管理 |
| 虚假成功率 | “加速包”“双通道”被监管点名 | 不承诺成功率；只展示可解释的状态 |
| 买短乘长/买长乘短 | 被监管认定为诱导，存在安全和法律风险 | 不默认推荐；只提示风险，不自动下单 |

## 8. 参考/自研结论

```text
查询/提交/回读/调度  →  参考 c66-m 的流程，自己实现
登录/锁座/支付页     →  参考 12306-helper 的流程，自己实现
通知/配置模式        →  参考 py12306 的接口，自己实现
校时/预热/购物车     →  参考 12306FairTicket 的算法，自己实现
隐私文档/边界        →  参考 RailWatch 的结构，自己写
功能标杆             →  Bypass（闭源，不碰代码）
```

**一句话**：高星项目给了“功能清单”，2026 年的新项目给了“可参考的流程”；自研只学算法和边界，不继承它们的 Cookie/反检测/许可证风险。
