# 00 · 一页纸结论

> 调研/审计截止：2026-11-14 · 所有星级/规则均为该日快照

## 一句话

**参考他们的算法，不继承他们的数据习惯；自研一个默认不落盘、只访问 12306、可审计的最小客户端。**

## 五个判断

1. **“开售自动买”有现成实现，但高星项目基本失效。** 34k 的 `testerSunshine/12306` 已于 2023-04 停更并归档；15k 的 `pjialin/py12306` 最后 push 是 2026-10，但核心代码、依赖和打码方案都是 2019 年的，196 个开放 issue。
2. **2026 年还在维护的项目，星都不高，而且都有数据安全短板。** `c66-m`（2★，MIT）会明文存会话 Cookie；`12306-helper`（0★，MIT）也明文存 Cookie；`12306FairTicket`（93★，无 LICENSE）默认高频；`RailWatch`（13★，MIT）有 `anti_detect.py`。详见 `docs/08-security-audit.md`。
3. **官方能力才是主战场。** 预填、起售提醒、候补（6 单 × 3 日期 × 60 车次）、京沪预约购票（开车前 30–17 天）已经把“卡点 + 排队 + 捡漏”做完了。第三方工具真正的价值是**编排**这些能力，而不是“刷得更快”。
4. **“一直监控”在售罄后基本是伪需求。** 12306 明确：车次进入候补状态后，新增票额优先兑现候补订单，此时不存在第三方所说的“余票监控”通道。正确动作是**第一时间提交候补**，不是挂机刷票。
5. **“占座”不是特权，是未支付订单。** 提交订单后席位保留到支付截止（通常 30 分钟），一个账号同时只能有 1 个未支付订单；一天取消/未支付合计 3 次，账号当天锁购票权限。多账号囤票既违规也容易被风控。

## 自研安全底线（摘要，完整 12 条见 `docs/08`）

| ID | 要求 |
|---|---|
| S-01 | 不存密码，只扫码登录 |
| S-02 | 会话 Cookie 默认只存内存；持久化必须 DPAPI + ACL |
| S-03 | 身份证号/手机号不落盘；内存用完清零 |
| S-04 | 只访问 `*.12306.cn`；无遥测/第三方 IP/CDN 扫描 |
| S-05 | 不反检测、不伪造指纹、不代理、不多账号、不打码 |
| S-06 | 日志/截图脱敏；不记录请求/响应体 |
| S-07 | 依赖锁定+哈希；不自动下载二进制；更新签名校验 |
| S-08 | 一键停止、退出清理、全盘加密建议 |

## 关键数字（落地时会变，以官方页面为准）

| 项目 | 数值 |
|---|---|
| 预售期 | 15 天（含乘车日） |
| 售票时间 | 05:00–次日 01:00；周二 05:00–24:00 |
| 候补订单 | 每账号 6 个待兑现；每单 3 个日期；合计 ≤60 个车次；≤19 位乘车人 |
| 候补截止 | 不晚于开车前 20 分钟；系统 24 小时兑现 |
| 候补预付款 | 按订单最高票价；支付后生效；未兑现原额退 |
| 订单支付 | 通常 30 分钟；临近发车更短；以页面提示为准 |
| 取消限制 | 一天内未支付/取消合计 3 次，账号当日锁购票 |
| 京沪预约试点 | 开车前第 30–17 天；每账号 3 个待兑现；每单连续 2 日、3 个精确 + 2 个模糊；兑现当日 23:00 前支付 |
| 2026 中秋国庆风控 | 慢速队列 711.7 万笔；拒绝出票 102.3 万笔/133.1 万张 |

## 一页纸决策

| 问题 | 答案 |
|---|---|
| 有没有现成软件？ | 有，见 `docs/01`；但 2026 年没有“高星 + 活跃 + 数据安全 + 许可证清晰”四者兼备的 |
| 直接用哪个？ | 不想折腾：官方 App；愿意承担风险：Bypass/12306FairTicket；重视隐私：自研 |
| 自己写值不值？ | 如果重视私人数据安全，值；参考算法 + 2–4 周，能做出最小可用版 |
| 最难的技术点？ | 不是下单接口，是**时间精度 + 幂等 + 风控边界 + 数据不落盘** |
| 最大风险？ | 明文 Cookie/账号被抄；高频锁号；付费代抢/多账号/打码可能触刑；见 `docs/05`、`docs/08` |
| 建议下一步 | 2 天安全 spike：DPAPI Cookie、临时 profile 清理、网络白名单、日志脱敏；全过再写 UI |
